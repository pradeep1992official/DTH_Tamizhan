# YouPI integration notes — new connections

Reviewed upstream commit `405327c27d78ae9d0dccdb1e2d2426cefc359477` (source checkout inspected, then moved outside application test discovery). Sources: [README](https://github.com/youpi-pg/YouPI-PG/blob/405327c27d78ae9d0dccdb1e2d2426cefc359477/README.md), [merchant contract](https://github.com/youpi-pg/YouPI-PG/blob/405327c27d78ae9d0dccdb1e2d2426cefc359477/docs/MERCHANT_INTEGRATION.md), `apps/payment-api/src`, `packages/core/src/webhook-engine.js`, `packages/core/src/statement-reconciliation.js` and `packages/merchant-sdk/src`.

- The merchant server creates an INR/UPI checkout with `POST /api/v1/payments`, merchant ID/key headers, a merchant-owned `orderId`, exact decimal `amount`, idempotency key and allowed return URL. The response contains `paymentId`, merchant order ID and hosted `checkoutUrl`. Status is fetched server-to-server with merchant credentials from `/api/v1/payments/:paymentId`. The existing recharge adapter already implements this HTTP transport; the new adapter reuses it.
- YouPI is a separately hosted Node/SQLite service, with a checkout portal and bank-connected Android SMS/notification, Gmail and Google Messages observers. Receiving-bank funds move outside this website. Observer infrastructure, credentials, Gmail access and uptime belong to the gateway operator; do not embed these credentials in the storefront.
- Bank alerts lack arbitrary merchant metadata. A single active payment slot per receiving VPA and amount/time/reference matching attempt to attribute alerts. Identical amounts, late/missing/forged alerts and replay can still be ambiguous. No bank API or automatically authenticated bank-statement feed is provided.
- Current upstream **does** send signed observation webhooks: `X-Gateway-Signature` authenticates raw bytes with HMAC-SHA256. V2 additionally signs `timestamp + '.' + rawBody` and includes a stable delivery ID and first-signing timestamp. Browser redirect/checkout success messages are not payment proof. The README's experimental/not-certified/not-production-ready warning still applies.
- `OBSERVED_SUCCESS` means an observer matched an alert; `RECONCILED` means an operator-imported CSV matched receiving account, amount and reference. An HMAC proves which gateway sent a message, **not bank settlement**. Even imported CSV is operator input. `SUCCESS` can mean COD/counter placement and is not UPI settlement.
- Therefore new-connection YouPI observations can only move to `awaiting_admin_confirmation`, never automatically to `paid`, including RECONCILED. The admin must independently check the receiving bank and enter/check the exact due amount and 12-digit UPI reference. Timeouts/failed/expired provider sessions stay pending and enter the admin verification queue; customers must not be told to pay again while an earlier debit is uncertain.
- The feature flag defaults off, and no provider is enabled by default. Signed callbacks require matching merchant order/payment IDs, INR, UPI and exact server amount. Duplicate deliveries are harmless; delayed observations are held for admin review. No browser redirect or unsigned/forged callback changes payment state. All YouPI refunds are manual bank transfers; no automatic refund implementation is added.
- Existing recharge behavior is deliberately unchanged. Its current observer-acceptance policy is different from this new-connection policy; these notes do not certify that older flow.

Safe scope: disabled-by-default integration with manual bank reconciliation. Automatic settlement approval cannot be implemented safely from this upstream contract and is intentionally unavailable. No live payment or bank observer was exercised during this task.
